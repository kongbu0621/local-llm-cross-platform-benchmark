# Qwen3.8-27B / GX10 — 完整结果、稳定性与硬件验证详情（2026-09-03）

本页是 README 首页结果总表的完整分表。目标不是只给最终 `decode tok/s`，而是把本轮已经真实取得的 **Formal5、Formal100、分位数/标准差、衍生指标、失败记录、Runtime/Hardware Gate、profiler 过程数据与结论边界** 都挂到同一条可核对证据链上。

> **重要语义：** 当前 Formal5 / Formal100 工作负载是 **32,768 input + 256 output**。它不是仓库定义的 `E2E@32K`（32,768 input + 32,768 output）。以下性能结论只对本轮短输出 workload 成立。

<a id="metric-guide"></a>
## 1. 指标逐项解释与公式

| 指标 | 含义 | 趋势 | 本轮如何得到 | 不能误解为 |
| --- | --- | --- | --- | --- |
| TTFT (ms) | 从请求发出到首个输出 token 到达的 wall-clock 时间 | 越低越好 | `vllm bench serve` 直接测量 | 纯 prefill kernel 时间 |
| TPOT (ms/token) | 首 token 之后，每个输出 token 的平均耗时 | 越低越好 | runner 直接测量 | 整个请求的平均 token 时间 |
| Decode / TG (tok/s) | 首 token 之后的持续生成速度 | 越高越好 | **派生：`1000 / TPOT(ms)`** | Output throughput |
| E2E (ms) | 请求发出到第 256 个输出 token 完整接收的总 wall-clock | 越低越好 | runner 直接测量 | 仓库固定的 `E2E@32K` |
| Effective PP (tok/s, derived) | 用输入 token 数除以 TTFT 得到的“有效输入处理速度” | 越高越好 | **派生：`32768 / (TTFT_ms / 1000)`** | 纯 Prefill throughput |
| Pure Prefill / `pp_tps` | 只计算 prompt prefill 阶段本身的吞吐 | 越高越好 | **本轮未单独测量** | 不允许拿 Effective PP 直接改名 |
| ITL (ms) | 相邻输出 token 之间的 latency | 越低越好 | runner 直接测量 | TPOT 的完全等价物 |
| Output throughput (tok/s) | 整个 benchmark wall-clock 下的输出 token 吞吐 | 越高越好 | runner 直接报告 | 单请求 decode speed |
| Total token throughput (tok/s) | 输入+输出 token 除以整个 benchmark 时间 | 越高越好 | runner 直接报告 | pure prefill 或 decode |
| Std / CV | 同一批请求的离散程度；`CV = std / mean` | 越低越稳定 | 标准差 + 本页派生 CV | 跨不同 run 条件的稳定性证明 |
| P50/P90/P95/P99 | 延迟尾部分布 | 越低越好 | runner 直接报告 | 长时间 24h 稳定性 |

**Pure Prefill 当前必须显示为 `未单独测量`。** 现有 `vllm bench serve` 的 TTFT 同时包含 API/调度、prefill、首 token 生成与返回链路，不能反推出严格的纯 `pp_tps`。本页保留 `Effective PP` 作为有用但有明确边界的衍生指标。

### 4.5 稳定性结论

- **完成率：** BF16 / FP8 / NVFP4 Formal100 均为 `100/100`，本轮正式 32K+256 workload 没有请求级 failure。
- **均值稳定：** FP8 与 NVFP4 从 Formal5 到 Formal100 的 TTFT / TPOT / E2E 漂移基本都在约 ±0.5% 内，说明本轮短输出工作负载下阶段结果和正式长批次均值高度一致。
- **尾延迟：** 三种精度 Formal100 的 TTFT P99 相对 mean 高约 3.3%～4.0%，E2E P99 相对 mean 高约 2.7%～3.4%；存在尾部，但未见数量级异常。
- **BF16 特性：** 多轮 5-request 过程数据说明 BF16 对运行阶段/状态更敏感；最终 Formal100 反而比早期 Formal5 更快，因此应以 Formal100 为正式基线，并保留阶段 run 作为过程证据。
- **结论边界：** 这只证明 `32K input + 256 output / concurrency=1` 的批次稳定性；**不能外推为 32K 长输出、256K/512K/1M 上下文、24h soak 或语义质量稳定性**。

## 5. FP8 / NVFP4 Runtime + Hardware Gate — 完整验证过程

这部分是本轮耗时最多、也最容易在最终汇总里被“压缩掉”的证据。它的目标不是跑一个速度数字，而是证明 **checkpoint → runtime 路由 → 真实 inference → GPU kernel → Nsight Compute 硬件计数器** 的整条链实际成立。

| Checkpoint identity | FP8 E4M3；dynamic activation；weight block `128x128` | checkpoint FP8 合同确认 |
| Runtime | vLLM 0.28.0；`quantization=fp8`；runtime dtype BF16 | 运行时确实走 FP8 quantization，不等于整模型所有模块均 FP8 |

<a id="conclusions"></a>
## 7. 本轮可以成立的结论

1. **性能：** 在 1× GX10、Qwen3.8-27B、32K input + 256 output、Concurrency=1 的本轮 Formal100 下，NVFP4 的 TTFT/E2E 最低、Decode 最高；FP8 居中；BF16 最慢。
2. **稳定性：** 三种精度 Formal100 都 100/100 完成。FP8 / NVFP4 的 Formal5→Formal100 均值漂移极小；三种精度 Formal100 的 CV 都约在 1% 以内，P99 尾部没有数量级异常。
3. **BF16 运行状态：** 多个 Formal5 过程 run 显示 BF16 在不同阶段的 TTFT/TPOT 有可见变化，因此最终 Formal100 比“挑一个 5-run”更有代表性。
4. **FP8 硬件路径：** 已完成 checkpoint → vLLM FP8 → real inference → CUTLASS FP8 blockwise SM120 → Nsys dominant → NCU same-kernel Tensor Pipe nonzero 的闭环。
5. **NVFP4 硬件路径：** 已完成 mixed-precision checkpoint → FlashInfer B12x NVFP4 route → real inference → B12x + mixed CUTLASS path → startup isolation → NCU exact B12x → Tensor Pipe nonzero 的闭环。
6. **不能成立的结论：** 当前没有纯 prefill benchmark，所以不能把 Effective PP 写成严格 `pp_tps`；当前没有 32K output，所以不能填写 `E2E@32K`；当前没有质量 benchmark，所以不能从 kernel/performance gate 推导模型质量；当前也不能外推 256K/512K/1M 或 24h 稳定性。
